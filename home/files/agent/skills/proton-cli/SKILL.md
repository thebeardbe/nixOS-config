# proton-cli

**Before using `proton`, run `proton skill --body-only` and follow what it prints.**
That output is generated by the installed build, so it always names the exact
commands your `proton` actually has. Do not rely on remembered syntax.

## Essentials

- The command is `proton` (alias `proton-cli`).
- Grammar is uniform: `proton <app> <collection> <verb> [TARGET...] [--flags]`.
  Apps are `mail`, `drive`, `calendar`, `contacts`, `account` and `api`.
- Sign-in is interactive and never takes a password on the command line:
  `proton account login` asks for email, password and 2FA at the terminal.
- Profiles keep accounts apart. `proton account login --profile work`, then
  `--profile work` or `PROTON_PROFILE=work` on each command.
- Machine-readable output: `-o json` or `-o yaml`.
- Every mutating command takes `--dry-run` to preview without applying.
- Confirmations: `--confirm` / `PROTON_CONFIRM` (for example `deletions=deny`).
  The strictest source wins, so a policy cannot be weakened at runtime.

## Safety for autonomous use

- Prefer a read-only policy when the task only reads. `PROTON_CONFIRM='mutations=deny'`
  refuses every change; `deletions=deny` refuses only permanent removals.
- Keep request volume plausible. Proton treats high rate or volume as abuse,
  and that is an account problem, not a tool problem.
- The session file is the credential. Never copy it out of the sandbox, and
  revoke it (`proton account sessions revoke`) when the task is done.

## Sharing files between machines

Two convenience wrappers are installed:

- `proton-push <local-path> <remote-folder>` — upload a file or directory.
  Re-uploading a name keeps the previous version as a revision.
- `proton-pull <remote-path> <local-dir>` — download a file or directory.

These are thin wrappers over `proton drive items upload` / `download`. There is
no watcher, no daemon and no conflict resolution: a push is not a sync, and
re-running it re-uploads rather than skipping unchanged files.
